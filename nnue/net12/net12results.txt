Net12 methodology
=================

Goal
====

Net12 is architecture work, not another attempt to squeeze the old line.

The current release fallback is net5_final.nnue, from the Chess768/256 line.
Net5 is being re-pinned against HCE after the classic feature-index bug was
fixed. That bug made classic nets use the king-file flip intended for bucketed
nets; the fixed engine now routes classic nets through plain Chess768 indexing.

We should not pivot back to Chess768 for net12. Net6/net7 already explored
continuation around that family and did not produce a clean next step. Net8,
net10, and net11 then explored KB8/256. They looked self-consistent inside the
KB branch, but direct HCE tests showed the branch was not actually stronger
than HCE:

- net10 vs HCE, small sample: -60.7 +/- 88.8 Elo.
- net8 vs HCE, small sample: -70.4 +/- 81.4 Elo.
- net5 vs HCE after the classic-index fix: +105.8 +/- 94.3 Elo.

The conclusion is not "go back to Chess768." The conclusion is that KB8/256
failed the only anchor that matters. Net12 should keep moving forward, but with
HCE sanity tests as the first gate instead of the last gate.

Architecture
============

Chosen architecture: KB16/256.

Reasoning:
- KB8 was too coarse or otherwise failed to translate internal gains into real
  HCE strength.
- Chess768/256 has already been mined hard enough for now.
- KB16 keeps the same hidden size and broad training pipeline as KB8, but gives
  the net twice as many king buckets:
  - 4 mirrored king-file buckets.
  - 4 rank bands, each two ranks tall.
  - 16 total buckets.
- This is a conservative next architecture: more spatial context than KB8
  without jumping straight to a much wider and slower net.

This run starts from scratch. It does not resume from net5, net8, net10, or
net11. Cross-architecture resume would confuse the experiment and is not
supported by the saved format.

Implementation
==============

Engine:
- `include/nnue.h` supports classic Chess768, KB8, and KB16 indexing.
- Classic nets with one king bucket use plain Chess768 indices.
- Bucketed nets use mirrored king-file indexing.
- KB8 uses 2 rank halves x 4 mirrored file buckets.
- KB16 uses 4 two-rank bands x 4 mirrored file buckets.

Loader:
- `src/nnue.cpp` accepts both 8-bucket and 16-bucket bucketed files.
- Classic files remain separate through `feature_set == FEATURE_SET_CHESS768`.

Converter:
- `nnue/convert_bullet.py` defaults to 16 king buckets.
- It accepts `--king-buckets 1`, `8`, or `16`.

Bullet trainer:
- Example: `shayveri_kb16`.
- Train id: `shayveri_v2.11_kb16`.
- Hidden size: 256.
- Output format: same SHAYVERI saved layout as the KB8 trainer, with the input
  layer expanded to KB16.

Training recipe
===============

NFS root:
- `~/nnue_v2_11`

Data:
- `POSITIONS=1000000` per chunk.
- `NODES=10000`.
- Worker source pattern: `NNHHHHHHHH`.
- Master source schedule: 20% NNUE chunks, 80% HCE chunks.

Reasoning for 80/20:
- Net9/net10/net11 showed that pure or near-pure branch self-play can create
  nets that look good only against their relatives.
- HCE must remain the anchor, but a new architecture still needs some current
  NNUE distribution to avoid learning only old HCE habits.
- 80/20 is a compromise between HCE anchoring and modern-policy coverage.

Optimizer defaults:
- `LR=0.001`
- `LR_AFTER_DROP=0.0003` at chunk 100.
- `SECOND_LR_AFTER_DROP=0.0001` at chunk 200.
- `EPOCHS=1`
- `BATCH_SIZE=16384`
- `WDL=0.1`
- `SCALE=400`

Testing plan
============

Do not wait for a long run to learn that the anchor is broken.

Early conversion checkpoints:
- Convert iter000, iter003, iter009, iter014, and iter019.
- Also convert any obvious local minimum/peak if training loss gives one.

First gate: HCE sanity.
- Test each early checkpoint directly against SHAYVERI_HCE at 10+0.1.
- Use the same opening book and options as the recent HCE checks.
- Track color split explicitly.
- If the best early KB16 checkpoint is meaningfully below HCE by iter019, kill
  the run.

Second gate: net5.
- Only after a checkpoint clears HCE should it be tested against
  net5_final.nnue.
- Use net5 as the release/champion anchor, not net10/net11.

Third gate: longer time control.
- Any checkpoint that beats or clearly ties net5 at 10+0.1 gets a 90+0.5 check.
- Do not claim a release improvement from STC alone if LTC regresses.

Useful scan command shape
=========================

For checkpoint pools, keep all engine options identical:

cutechess-cli \
  -engine name=iter000 cmd=./SHAYVERI dir="." proto=uci option.OwnBook=false option.EvalFile="iter000.nnue" \
  -engine name=iter003 cmd=./SHAYVERI dir="." proto=uci option.OwnBook=false option.EvalFile="iter003.nnue" \
  -engine name=iter009 cmd=./SHAYVERI dir="." proto=uci option.OwnBook=false option.EvalFile="iter009.nnue" \
  -engine name=iter014 cmd=./SHAYVERI dir="." proto=uci option.OwnBook=false option.EvalFile="iter014.nnue" \
  -each tc=0.5+0.05 option.Hash=64 option.Threads=1 \
  -rounds 1 \
  -games 200 \
  -repeat \
  -concurrency 23 \
  -ratinginterval 250

For HCE pinning, use the recent direct anchor shape:

cutechess-cli \
  -engine name=SHAYVERI     dir="." cmd=./SHAYVERI option.EvalFile=iter009.nnue \
  -engine name=SHAYVERI_HCE dir="." cmd=./SHAYVERI_HCE \
  -each proto=uci tc=10+0.1 option.Threads=1 option.Hash=64 \
  -games 300 \
  -repeat \
  -openings file=../books/8moves_GM_LB.epd format=epd order=random \
  -concurrency 23 \
  -draw movenumber=40 movecount=8 score=10

Kill conditions
===============

Kill the run if:
- KB16 repeats the KB8 pattern: good internal Elo, bad HCE.
- No checkpoint through iter019 is at least competitive with HCE.
- Color split is badly asymmetric in the HCE gate.
- Validation finds bad positions or conversion mismatches.
- Training cannot produce a legal KB16 file that the engine loads cleanly.

Success condition
=================

Minimum useful result:
- KB16 clearly beats HCE at 10+0.1, then becomes competitive with net5.

Release-worthy result:
- KB16 beats net5_final.nnue at 10+0.1 and does not regress at 90+0.5.

If KB16 fails:
- Stop bucket-count-only experiments for now.
- The next useful direction is a real representational change, such as wider
  hidden size, richer features, or a different bucket layout.
