Net9 methodology
================

Goal: continue the successful KB8/Bullet direction from net8 while fixing the
chunk delivery and disk-pressure problems that contaminated the net8 tail.

Baseline
========

Net8 proved the KB8/Bullet architecture:
- KB8 from scratch reached net5 strength quickly.
- `net8_019` scored +10.1 +/- 19.3 Elo vs net5 over 1000 games.
- The clean net8 checkpoint ladder peaked around iter029/iter049 before disk
  pressure corrupted later chunks.

Net8 winner selection:
- Fast playoff favored iter029 over iter049:
  `Score of iter029 vs iter049: 345 - 274 - 181 [0.544] 800`
  for +30.9 +/- 21.2 Elo.
- Net9 therefore resumed from net8 iter029.

Net9 changes from net8
======================

- Same KB8 architecture.
- Same Bullet trainer and strict `convert_bullet.py` format.
- Same controlled 80/20 HCE/NNUE source schedule.
- Chunk size dropped from 5M positions to 1M positions.
- NFS root changed to `~/nnue_v2_8`.
- Train id changed to `shayveri_v2.8_kb8`.
- Master validates every shuffled Bullet file before training.
- Master rejects chunks below the minimum expected line count before training.
- Worker refuses to start/publish a chunk when free disk is below the configured
  safety threshold.
- Worker source order is configurable with `SOURCE_PATTERN`; default is
  `NNHHHHHHHH`, and reverse feeder workers can use `NNNNNNNNHH`.

Reason for 1M chunks
====================

With 8 workers, the old 5M chunk size allowed too much data to sit in
`incoming/` and `ready/`. In net8 this led to disk exhaustion and malformed
chunks around the 070s. Smaller chunks reduce queue pressure, improve source
delivery timing, and make failures cheaper.

Validated setup
===============

- `POSITIONS=1000000`.
- `NODES=10000`.
- `WDL=0.1`.
- `SCALE=400`.
- `BATCH_SIZE=16384`.
- `EPOCHS=1`.
- `LR=0.001`; no LR overrides were used in the valid run.
- Default worker `SOURCE_PATTERN=NNHHHHHHHH`.
- Resume from net8 iter029 via `INITIAL_RESUME`.
- On restart, if `state/latest_checkpoint.txt` exists, master resumes from the
  latest net9 checkpoint instead of returning to the net8 checkpoint.

Conclusion
==========

Net9 is not a promotion candidate and should not be continued.

The valid net9 run proved that the fixed 1M Bullet pipeline can train legal,
non-collapsed checkpoints, but it did not produce a stronger net than net8. The
critical result is the 10+0.1 match: iter039 looked playable as White but
collapsed as Black. That suggests net9 drifted into a color/side imbalance or
fast-TC overfit rather than real strength.

The best current KB8 checkpoint remains net8 iter029 / `net8_final.nnue`.

Main lessons for net10
======================

- Do not continue from net9.
- Restart from net8 iter029.
- Keep the fixed 1M chunk pipeline and validation; those parts worked.
- Change the training recipe to reduce drift from net8's balance.
- Test candidates at 10+0.1 earlier; fast 0.5+0.05 pools were too optimistic.
- Pay close attention to White/Black split, not just aggregate Elo.

Resolved blockers from earlier failed net9 attempts
===================================================

These issues affected discarded net9 attempts and are fixed now:

- `RESUME` was initially passed by the master but ignored by
  `nnue/shayveri_kb8.rs`, so early net9 checkpoints were not continuations.
- Bullet checkpoint paths initially missed the `-1` superbatch suffix.
- `batches_per_superbatch` was initially hardcoded to 6104, causing each 1M chunk
  to be replayed roughly 100 times. The master now computes it from actual line
  count divided by `BATCH_SIZE`.
- Illegal move losses were caused by UCI/search lifecycle bugs, not by net9
  training. `src/uci.cpp` now stops and joins active searches before accepting a
  new position, final bestmoves are legality checked, and Lazy SMP threads use
  private TT instances.
